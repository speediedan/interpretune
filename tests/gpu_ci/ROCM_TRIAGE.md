## Regenerating and extending

```bash

python tests/gpu_ci/phase_manifest.py --phase cuda --phase standalone \
    --out tests/gpu_ci/phase_collection_manifest.json
```

## Build-day (T0) execution and classification

When AMD hardware is present, in a ROCm torch environment under the host GPU lease:

```bash
export GPU_LEASE_CMD=<path to gpu_lease.sh>
$GPU_LEASE_CMD -- env IT_RUN_CUDA_TESTS=1 python -m pytest tests src/it_examples/tests -v 2>&1 | tee rocm-cuda-phase.log
bash ./tests/special_tests.sh --mark_type=standalone --allow-failures
$GPU_LEASE_CMD -- env IT_RUN_CUDA_TESTS=1 python -m pytest tests/gpu_ci/test_latent_device_placement.py -v -rA --junitxml=g6.xml   # issue 795
python tests/gpu_ci/phase_manifest.py --classify-file rocm-cuda-phase.log
python tests/gpu_ci/phase_manifest.py --classify-junit rocm-cuda-phase.junit.xml   # every failure, cascades attributed
```

Report *collected beside passed, by phase name* for every run. Then sort each failure with
`classify_failure` (also `--classify-file` above) into exactly one bucket:

| bucket | meaning | fix shape |
| --- | --- | --- |
| `cuda-only-dependency` | an import or library ships only for CUDA | replace or gate the dependency |
| `rocm-kernel-gap` | HIP reached the op and does not implement it (rocBLAS, MIOpen, HIP kernel) | upstream gap: record, skip narrowly |
| `backend-gap` | a backend capability is missing (distributed backend, device type, capability probe) | backend work or a capability-gated skip |
| `device-fault` | a kernel faulted on the device (device-side assert, illegal memory access, `hipErrorLaunchFailure` / `unspecified launch failure`, an HSA exception); not ROCm evidence by itself, since an out-of-range index faults on either vendor | find the first fault's cause, often a real bug that depends on test order or cached inputs |
| `device-fault-cascade` | (`--classify-junit` only) a later device fault in the same process: the poisoned context re-reporting the first fault, which `first_fault` names | none of its own; fix the first fault |
| `hip-compatible-cuda-interface` | the `torch.cuda` HIP-compatibility surface works; the failure is an NVIDIA assumption (device name, `nvidia-smi`, a CUDA version string) | make the assumption vendor-neutral; expect the test to run on ROCm |
| `resource-calibration` | a measured resource (a memory-profiler stat) differs from the expectation recorded on another device | recalibrate per device, or widen the tolerance with the measured spread |
| `numerics-tolerance` | device values differ from a reference beyond the test's tolerance (`torch.testing`'s mismatched elements and greatest difference) | compare the measured difference with the vendor's kernels before touching the tolerance |
| `unknown` | no bucket matched | triage by hand; never guess |

A device fault is sticky: every later GPU test in the same pytest process fails with it. Measured on
the 2026-10-23 parity runs, one out-of-range gather became 1 fault plus 48 cascade failures on each vendor,
so classify a phase with `--classify-junit`, which reads the JUnit file in execution order and reports
the cascade against its first fault, rather than counting 49 faults.

The classifier's contract (bucket order, `unknown` on a miss) is pinned by sanitized planted
failures in `test_phase_manifest.py`, so the triage paths are exercised before hardware
exists. The patterns are deliberately narrow: a real ROCm failure that lands in `unknown` is
the honest outcome and the signal to extend a pattern with the measured text.

## Calibrations from the 2026-10-24 AMD reruns

Measured on two AMD Radeon AI PRO R9700 (torch 2.15.0+rocm10.0, HIP 7.15) at `2d0d0887`, on a fresh datasets
cache: the cuda phase collected 110, with 100 passed, 2 failed, 8 skipped, and **no device faults**. Both failures and
the profiling failure were sorted and calibrated as follows, each scoped so NVIDIA keeps its expectation:

| Failure | Bucket | Measured (three runs) | Calibration |
| --- | --- | --- | --- |
| `test_l_profiling[test_cuda_32_l]` | `resource-calibration` | `reserved_bytes.all.peak` 689963008 against 576716800 (+19.6%), identical in all three; the allocated stats and `npp_diff` pass | a ROCm override (`expected_mem_rocm` in `profile_memory_footprints.yaml`) for that stat only, at the default 10% tolerance: the HIP caching allocator sizes its segments differently, and the allocated bytes agree |
| `TestCircuitTracerConformance::test_mixed_modes_apply_in_declaration_order` | `numerics-tolerance` | the commuting control (two adds in opposite orders) at 1.07e-4 to 1.47e-4 against `atol=1e-4`, 3 of 3 | `ROCM_COMMUTE_ATOL = 3e-4` on a ROCm device |
| `TestCircuitTracerConformance::test_batched_hooks_agree_with_sequential` | `numerics-tolerance` | 2 of 3 failed identically (104,923 of 149,422,080 logits, 7.0e-4, beyond the padded tolerance; greatest 3.13e-2), 1 of 3 agreed | on a ROCm device, at most `ROCM_BATCHED_MISMATCH_FRACTION = 1.5e-3` of the logits beyond the padded tolerance and none beyond `ROCM_BATCHED_ATOL = 6e-2` |

**Revised after the first CI run on the AMD agent (az 1692, in the job container):** the commuting control measured
1.373e-4 but was still checked against 1e-4, because its logits come back on the CPU and the ROCm scope read the
tensor's device; it is now decided from the suite's device. Batched hooks measured 375,886 logits (2.52e-3) beyond the
padded tolerance, greatest 8.54e-2, in float32. That is far beyond roundoff and varies run to run, so it is not
widened further: on ROCm the case records a non-strict xfail with the measured numbers (interpretune#818) when the
bound is exceeded, after its positive control has run.

Each ROCm bound is about twice the measured spread. For the batched case, a bounded fraction was chosen over a
uniformly wider tolerance, which would loosen all 149 million logits sixty-fold, and over a ROCm skip, which would drop
the check: 99.9% of the logits still meet the padded tolerance, and the case's positive control still guards against
a vacuous pass. The profiling failure stopped at the first stat; the stat check now reports every stat that differs
in one failure, so one run measures all four.

## Issue 795 placement tests

`test_latent_device_placement.py` now meets the G-6 contract with a real model split across
two devices. Its first version did not: a contract review of `a2e432e6` found that none of its
four CUDA tests built a model or performed a cross-device operation, that its device
assertions compared a tensor with itself, and that its optimizer check iterated an empty
SGD state. Its NVIDIA **4 of 4** (2026-10-19, under the lease) is therefore recorded as
*placement smoke*, not G-6 acceptance, and ROCm runs the revised file.

The revised file:

- keeps the seeded single-device CPU reference for `ablate_sae_latent` and
  `project_embeddings`, and compares single-device CUDA inputs with it **exactly** (both ops
  compute identical float32 values);
- loads gpt2 with an explicit dict `device_map` (blocks 0 to 5 and the tied
  embedding/unembedding on `cuda:0`, blocks 6 to 11 and the final norm on `cuda:1`), asserts
  the parameter devices are exactly `{cuda:0, cuda:1}` as a positive control, and compares
  with the same model on `cuda:0` alone;
- splices `gpt2-small-res-jb` SAEs into block 9 (`cuda:1`) for SAE latents, their projection
  and an `ablate_sae_latent` hook (a latent active in every prompt, with a positive control
  that the ablation moves the logits), and into block 1 (`cuda:0`) for an Adam step whose
  gradient crosses back from `cuda:1`;
- asserts devices only on outputs of cross-device operations and on module parameters after
  a pass, and asserts Adam state is non-empty and sits with its parameters.

Tolerance for split against single-GPU is `1e-3` absolute and relative, in float32 with TF32
disabled: the second half runs on a different card and kernel set, which reorders float32
rounding but cannot produce the order-of-magnitude differences a placement defect does.
NVIDIA validation of the revised file, 2026-10-19, under the host GPU lease after the
maintainer's first-person go: file collection 8, cuda-phase selected 6, **6 passed** (7.1 s;
Python 3.13.11, torch 2.13.0+cu130, transformers 5.16.1, sae_lens 6.50.0, RTX 4090 as
`cuda:0` + RTX 2070 SUPER as `cuda:1`). Measured split against single-GPU maximum absolute
differences, recorded as junit properties by the tests themselves: SAE latents `3.1e-4`,
ablated logits `9.2e-5`, SAE gradients `1.1e-6`; the ablation's own effect on the logits is
`1.13`. Repeated the same day on the torch 2.15.0 release candidate (test channel, `+cu130`;
transformers 5.20.2, sae_lens 6.51.1), again under the lease: collected 8, selected 6,
**6 passed**, with the same measured differences to the last bit. That is an NVIDIA result
only; ROCm runs this file at hardware time.

## Findings recorded while preparing

- `project_embeddings`' PCA path is nondeterministic across unseeded calls (randomized
  `torch.pca_lowrank`, no seed plumbed): measured 2026-10-19, two calls on one CPU input
  differed in every coordinate (max difference 5.67). The placement tests therefore seed
  immediately before each call so placement is the only variable. Whether the projection
  itself should take a seed is a separate change, not made here.
- The `tests collected` line pytest prints under a phase selector counts pre-selection
  items; the manifest parser counts the selected node ids actually listed. Those numbers
  differ (for example 3554 printed against 103 selected for the cuda phase before this
  branch's tests), which is exactly why the manifest records node ids, not the printed line.
