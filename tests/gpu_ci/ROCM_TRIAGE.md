## Regenerating and extending

```bash
# from the repository root, any CPU-only environment (no GPU, no lease)
python tests/gpu_ci/phase_manifest.py --phase cuda --phase standalone \
    --out tests/gpu_ci/phase_collection_manifest.json
python tests/gpu_ci/phase_manifest.py --phase baseline   # counts only, to stdout
```

This reuses the existing collection shape (`tests/gpu_ci/calibrate.py`, `gpu_phase.sh`)
rather than a new driver: one `pytest --collect-only` subprocess per phase with the phase's
own selector env.

## Build-day (T0) execution and classification

When AMD hardware is present, in a ROCm torch environment under the host GPU lease:

```bash
export GPU_LEASE_CMD=<path to gpu_lease.sh>
$GPU_LEASE_CMD -- env IT_RUN_CUDA_TESTS=1 python -m pytest tests src/it_examples/tests -v 2>&1 | tee rocm-cuda-phase.log
bash ./tests/special_tests.sh --mark_type=standalone --allow-failures
IT_RUN_CUDA_TESTS=1 python -m pytest tests/gpu_ci/test_latent_device_placement.py -v   # issue 795
python tests/gpu_ci/phase_manifest.py --classify-file rocm-cuda-phase.log
```

Report *collected beside passed, by phase name* for every run. Then sort each failure with
`classify_failure` (also `--classify-file` above) into exactly one bucket:

| bucket | meaning | fix shape |
| --- | --- | --- |
| `cuda-only-dependency` | an import or library ships only for CUDA | replace or gate the dependency |
| `rocm-kernel-gap` | HIP reached the op and does not implement it (rocBLAS, MIOpen, HIP kernel) | upstream gap: record, skip narrowly |
| `backend-gap` | a backend capability is missing (distributed backend, device type, capability probe) | backend work or a capability-gated skip |
| `hip-compatible-cuda-interface` | the `torch.cuda` HIP-compatibility surface works; the failure is an NVIDIA assumption (device name, `nvidia-smi`, a CUDA version string) | make the assumption vendor-neutral; expect the test to run on ROCm |
| `unknown` | no bucket matched | triage by hand; never guess |

The classifier's contract (bucket order, `unknown` on a miss) is pinned by sanitized planted
failures in `test_phase_manifest.py`, so the triage paths are exercised before hardware
exists. The patterns are deliberately narrow: a real ROCm failure that lands in `unknown` is
the honest outcome and the signal to extend a pattern with the measured text.

## Issue 795 placement tests

`test_latent_device_placement.py` holds a single-device CPU reference for latent projection
(`project_embeddings`, PCA) and latent ablation (`ablate_sae_latent`), then repeats both on
one CUDA device and split across two CUDA devices, asserting equality with the reference,
declared-device placement, and parameter/optimizer movement for a stepped decoder. CPU
tests: 20 passed with the 4 CUDA tests skipped (GPUs hidden) on 2026-10-19. The CUDA tests
await the maintainer's authorization for this validation under the GPU lease (recorded as a
first-person ask by the preparing session); they have been *collected* (they are 4 of the
107 cuda-phase node ids above), not executed. The same file is the ROCm build-day target
unchanged: it names no NVIDIA-only surface. This is latent acceptance, distinct from J-space
fine-tuning.

## Findings recorded while preparing

- `project_embeddings`' PCA path is nondeterministic across unseeded calls (randomized
  `torch.pca_lowrank`, no seed plumbed): measured 2026-10-19, two calls on one CPU input
  differed in every coordinate (max difference 5.67). The placement tests therefore seed
  immediately before each call so placement is the only variable. Whether the projection
  itself should take a seed is a separate change, not made here.
- The `tests collected` line pytest prints under a phase selector counts pre-selection
  items; the manifest parser counts the selected node ids actually listed. Those numbers
  differ (for example 3554 printed against 103 selected for the cuda phase before this
  branch's tests), which is exactly why the manifest records node ids, not the printed line.
