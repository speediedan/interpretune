# Compact stand-ins for AGENTS.md

Read by `scripts/gen_agents_compact.py`, which builds the root `AGENTS.md` from `AGENTS.full.md`: every section of the
full file is copied verbatim EXCEPT the ones named below, which are replaced by the stand-in under their marker. A
stand-in keeps every rule and prohibition of its section and the commands a person needs most; it drops the measured
incidents, worked examples and long command listings, which stay in the full text.

Marker format: `<!-- section: <exact heading of the full section> sha=<first 12 hex of the section's SHA-256> -->`.
The `sha` is the full section as it was when its stand-in was last reviewed. When the full section changes, the
generator fails until the stand-in is re-read and `scripts/gen_agents_compact.py --update-hashes` is run. Do not
use this file for anything that is not a stand-in.

# AGENTS.md - Interpretune (compact form)

> This is the COMPACT form of the repository's agent instructions, generated by `scripts/gen_agents_compact.py` from
> `.agents/reference/AGENTS.full.md` for agent harnesses that cap how much instruction text they load (Muse Code
> reads 64 KiB across all of its instruction files; opencode and Codex read this file). Sections whose heading ends in

> that area. Claude Code reads the full file through `CLAUDE.md`. Do not edit this file: edit the full file and, for a

<!-- section: Build & Dev Environment sha=b09311b8a56b -->
Only three install flows exist:

| Flow | Command | Honors the uv overrides? |
| --- | --- | --- |
| User / README | `uv venv` then `uv pip install -e ".[examples,lightning]" --group git-deps --group test` | yes |
| Dev / CI, and pins-only validation | `scripts/build_it_env.sh` (no `--from-source` directives) | yes |
| Bare pip | `pip install .` | **not supported** |

`pip install .` fails in a way that looks like an application bug: pip ignores `[tool.uv] override-dependencies` (the
`transformer-lens==4.0.0` and `nnsight==0.7.0` pins), so it resolves a TransformerLens 2.x, and every downstream
failure (a `sae_dashboard` import error, `BertForPreTraining`) is a symptom of that resolution, not a defect to file.

Rules that must not be missed:

- **Never `pip install` into a dev venv** (`it_latest`, `it_release`, scratch envs), not even for one repair. pip
  ignores the overrides, can leave two `.dist-info` directories for one package, and defeats the audit that would
  catch it. Repair by rebuilding with `build_it_env.sh`; a true one-off is `uv pip install`. Before an env gates a
  release, an upstream PR or a benchmark artifact, audit it: any `<site-packages>/*.dist-info/INSTALLER` that reads
  `pip` is a finding.
- **"Validate in an env built FROM the pins" means `build_it_env.sh` with no `--from-source`.** A green local suite is
  not evidence that the pinned dependency set is green: editable installs can run ahead of the pins with an identical
  version string. Check `pip show <pkg> | grep -i location` or `direct_url.json`, not the version.
- **Prove which code ran with `__file__`, not a version string:**
  `python -c "import interpretune, torch, transformer_lens as tl; print(interpretune.__file__, torch.__file__, tl.__file__)"`.
- Venvs live under `/mnt/cache/$USER/.venvs` (the uv cache's filesystem, so hardlinks work). Variables: `IT_VENV_BASE`,
  `IT_TARGET_VENV`, `IT_REPO_DIR`. Build: `./scripts/build_it_env.sh --repo_home=${PWD} --target_env_name=${IT_TARGET_VENV} --venv-dir=/mnt/cache/$USER/.venvs`;
  CPU-only adds `--torch-backend=cpu`, and the whole torch ecosystem must share that backend (a torchvision from the
  default index is CUDA-linked and fails later with `operator torchvision::nms does not exist`).
- **From-source directives** (`--from-source="pkg:path:extras:ENVVAR=..."`) are for a repository you are actually
  developing: they take the package out of the pins' governance. `sae-lens` is git-pinned temporarily to
  decoderesearch/SAELens#739; the old fork pin `speediedan/SAELens@86f90b3d` must never come back (20 duplicate YAML
  keys bind 10 transcoder entries to the wrong weights). `UV_EXCLUDE` (the excludes file) is required on the
  sae_dashboard and circuit-tracer directives; install nnsight first; after every rebuild validate with
  `python requirements/utils/collect_env_details.py`.
- **Pins:** `pyproject.toml` `[tool.uv] override-dependencies` (keep in sync with `requirements/ci/overrides.txt` and
  `excludes.txt`) and `[dependency-groups] git-deps` (excluded from the universal lock, so every bump needs hand
  validation). The CI lock is regenerated with `./requirements/utils/lock_ci_requirements.sh`. A rebuild that changes
  benchmark-relevant dependencies must end with the dashboard parity gates green and a fresh benchmark wave.

<!-- section: Testing sha=f2eb4f426e26 -->
Basic run (mirrors `ci_test-full.yml`): `python -m pytest tests src/it_examples/tests -v`; add
`--cov=src/interpretune --cov-append --cov-report=` for coverage. Standalone tests take inline variables, never
`export` (marker conflicts): `IT_RUN_STANDALONE_TESTS=1 python -m pytest <node>`; the harness is
`./tests/special_tests.sh --mark_type=standalone [--filter_pattern=...]`. Profiling tests use `IT_RUN_PROFILING_TESTS=1`.
`special_tests.sh` is an entry script for gpu-epsilon's shared runner (`gpu_epsilon.special_tests`, pinned in
`requirements/ci/gpu_epsilon.txt`), configured by `[tool.gpu-epsilon.special-tests]` in `pyproject.toml`: change a mark,
a selection variable or the coverage command there, not in the script. Node outcomes come from per-rank records.

- **Phase marks** (`standalone`, `min_cuda_gpus`, `bf16_cuda`, `profiling`, ...) may sit on a test or on its class:
  collection reads `item.iter_markers()`, so a class-level `@RunIf(...)` selects every test the class collects,
  inherited ones included.
- **A GPU test is a last resort and declares its needs.** Write a CPU test unless the check depends on a device or
  cannot run on the hosted runners. A GPU test declares `RunIf(min_cuda_gpus=N, min_gpu_mem_gb=X)` with `X` measured
  by `tests/gpu_ci/calibrate.py`, never estimated, and a guard fails any GPU-marked test without it
  (`tests/README.md`, "GPU Tests: When to Write One, and What It Must Declare"). For memory-heavy tests prefer
  `@pytest.mark.usefixtures("cleanup_memory")` over the standalone workaround. CI reruns transient httpx/HF timeouts
  (`--reruns 2 --reruns-delay 5`).
- **Run long suites in the background**, never in the foreground or through `tee`: the basic suite takes about 30
  minutes and `gen_it_coverage.sh` about 50, and terminal lifecycle or OOM kills foreground runs. Use
  `nohup ... > log 2>&1 &` plus `disown`, or `scripts/manage_standalone_processes.sh --use-nohup scripts/gen_it_coverage.sh --repo-home=... --target-env-name=... --venv-dir=... --no-rebuild-base`
  (`--allow-failures --no-reruns` while debugging, `--resource-debug` for per-test and per-GPU logging). Kill any
  earlier run first, by exact PID.
- **Watch a background run with `scripts/watch_run.sh`**, which prints exactly one terminal line (`GREEN`, `RED`,
  `DEAD`, `TIMEOUT`, `QUERY-FAILED`) and exits. Subjects: `--pid PID --log FILE`, `-- CMD`, `--azure-build ID`,
  `--pr-checks N`, `--find PATTERN`. The rules behind it: never `pgrep -f` a pattern your own watcher command
  contains (it matches itself; use the bracket trick or watch the PID); prefer PID watches to output-grep watches
  (wording changes make them hang) and remember a zombie still answers `kill -0`; cover every terminal state.
- **Pre-PR-wave gate:** before a coordinated multi-repo PR wave a full `gen_it_coverage.sh` pass in
  `--run-all-and-examples` mode is mandatory, run AFTER refreshing the registered benchmarks (`tests/benchmarks/`),
  and its final run must be free of real failures. Then every remote check must pass too: the GitHub matrix
  (`ci_test-full`, `type-check`) and the self-hosted Azure GPU pipeline (`.azure-pipelines/gpu-tests.yml`, released by
  a ready-for-review PR to `main` or a manual run; approve per `.claude/skills/az-pipelines-ops/SKILL.md`).
- **A conflicting pytest process reported by the harness is a genuine other run** (an Azure CI container's suite is
  visible on the host and should block a local run). Check whether it is still active before starting a second one;
  kill stale collectors by exact PID, never `pkill -f "pytest..."` (the pattern matches its own command line).
- The local coverage harness runs four phases: `standard` (CPU-only, `CUDA_VISIBLE_DEVICES=''`), `standard gpu
  cuda-marked` (`IT_RUN_CUDA_TESTS=1`), `standalone gpu` and `CI Profiling`. For semantic concept-direction parity
  drift use the gate in `tests/core/test_analysis_backend_parity.py`.

<!-- section: Serializing GPU work on a shared host sha=714651a2e571 -->
The GPU host is shared by agent sessions in this repo, sessions in `finetuning-scheduler`, and the self-hosted Azure
agent. Two GPU suites at once contend silently (OOM, flaky timing), which is easily misdiagnosed as a test failure.

- `scripts/gpu_lease_wrap.sh` is an **opt-in** `flock` lease and a complete no-op unless `GPU_LEASE_CMD` points at a
  lease implementation. `export GPU_LEASE_CMD=/path/to/gpu_lease.sh`, then `tests/special_tests.sh` and
  `scripts/gen_it_coverage.sh` re-exec under it, so one acquisition covers a suite.
- Two keys: `gpu` and `cpu-heavy` (host memory). The two self-wrapping scripts take both by default
  (`GPU_LEASE_ARGS=--cpu-heavy`); GPU-only work wrapped with the plain lease (`$GPU_LEASE_CMD -- <cmd>`) may overlap CI's
  CPU phase.
- **Never force-reset a lease held by a CI job.** A CI-held lease shows project tag `azure-it-<buildId>` and a
  `[container]` marker: cancel the pipeline run instead.
- **Waiting is normal.** A run may sit at `'gpu' lease is held; waiting...` for as long as the holder runs (a CI job is
  about 37 minutes). Do not disable the lease or kill the holder.
- Notebooks and other interactive GPU work are not lease-aware by design: check `--status` first and, for a long
  session, reserve with `--hold` / `--release`.
- The `gpu-lease` skill (`.claude/skills/`, a vendored copy of the repo-neutral master in speediedan/skills: do not
  edit it here) covers planning and recovery from stuck or stale leases.

<!-- section: Architecture sha=04e43805ac06 -->
**Layout:** `src/interpretune/` holds `adapters/` (TL, SAE, Lightning, CircuitTracer, NNsight), `analysis/` (ops system
and dispatcher), `config/` (dataclass configs), `extensions/` (MemProfiler, DebugGeneration, NeuronpediaIntegration),
`runners/` (SessionRunner, AnalysisRunner), `utils/`, `protocol.py`, `registry.py` (ModuleRegistry, RegisteredCfg),
`session.py` (ITSession) and `base/components/cli.py`; `src/it_examples/` holds example experiments, configs and
notebooks; `tests/` has `core/`, `benchmarks/` (see `tests/benchmarks/README.md`), `*_parity/` and `examples/`.

**Key patterns:**

- **Lazy imports.** Heavy dependencies (transformer_lens, lightning, neuronpedia) load lazily via `_light_register.py`
  and PEP 562 `__getattr__`; import time matters (`tests/core/test_adapters_import_time.py` guards it).
- **Protocols and composition.** ITModuleProtocol, ITDataModuleProtocol, AnalysisOpProtocol; `CompositionRegistry`
  manages adapter combinations (core, lightning, transformer_lens, sae_lens, circuit_tracer, nnsight).
- **Backend-agnostic analysis ops.** Keep backend-specific imports out of the bundled op definitions
  (`src/interpretune/analysis/ops/bundled/<family>/<family>_ops.py`); extend the `AnalysisBackend` seam instead.
- **Framework-agnostic modules and logging.** Module definitions (e.g. `RTEBoolqSteps`) hold no framework-specific hooks
  or accumulation logic: use `ClassificationMixin`; hooks dispatch through `_call_itmodule_hook(..., optional=True)`;
  user code calls `self.log()` / `self.log_dict()` whatever the context.
- **Generation config.** `HFGenerationConfig` for HF-backed models; `CoreGenerationConfig` only for TL-native models.
- **User-facing op calls.** In notebooks, examples and one-off scripts use `import interpretune as it` and the
  top-level wrappers (`it.concept_direction(...)`); avoid `DISPATCHER.get_op(...)` outside dispatcher internals.
- **Type stubs** (`.pyi`) are generated by `scripts/generate_op_stubs.py` and must stay in sync.

**TransformerLens:** `TransformerBridge` is the only model path (no `use_bridge` flag: passing it fails by name).
HookedTransformer-equivalent numerics come from `enable_compatibility_mode()` on `ITLensBridgeConfig`; omit it for raw
HF weights. Config-only initialization goes through `TransformerBridge.boot_native`, which does not infer TL's `-1`
vocab sentinels, so the adapter resolves `d_vocab` / `d_vocab_out` first. Config hierarchy and what
`_capture_hyperparameters()` serializes: `docs/tl_config_hierarchy_overview.md`.
