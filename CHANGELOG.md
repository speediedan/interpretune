# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](http://keepachangelog.com/en/1.0.0/). Per the stability policy (`docs/source/stability.md`), every breaking change lands under a `### Breaking` heading naming the old and new form; a release check confirms the heading exists whenever such a change is in the release.

## [Unreleased]

### Breaking

- AnalysisStore envelopes are schema version 2, which requires a `subject` block: the model (id and resolved revision), architecture, tokenizer, component map and latent dictionaries the store was computed on. `AnalysisCfg.apply` stamps it from the module at write time; `push_analysis_store(..., subject=)` states it for a store assembled outside an op, and a store with neither is refused before any network call. `pull_analysis_store` restores it as `store.subject`. Version-1 envelopes are still read, without a subject ([#1008](https://github.com/speediedan/interpretune/issues/1008), [#283](https://github.com/speediedan/interpretune/issues/283))

- Pulling a store resolves its envelope's `protocol_cls` only from `interpretune` or a hub component module already loaded through the remote-code gate, and refuses any other path, an import failure, or a class that is not a batch protocol, rather than falling back to the default protocol ([#1008](https://github.com/speediedan/interpretune/issues/1008))

- `tunable_roles()` declares roles by address (speediedan/venngram#109): its mapping takes roles mapped to venngram addresses, which a view resolves against its own names and structure when it is built, as well as tensor names mapped to roles. The roles Interpretune declares are addresses: `module:latent_models.<name>` for an attached latent model, `module:interventions.<name>` for an intervention, the operands of a weight edit (`module:<edit> & leaf:<operand>`), `module:attached_saes.<key>` for a spliced SAE (whose buffers now take its role too, as a latent model's do), and a `name:` pattern for each LoRA adapter of a TransformerLens composition. A cooperative override merges its declarations with `interpretune.tuning.views.merge_roles`, which joins two addresses given for one role, rather than updating `super()`'s mapping by name; code that reads `tunable_roles()` as names expands it first with `expand_declared_roles(module, roles)`. `TransformerBridgeView` and the circuit-tracer composition's bound view take addresses too, and `latent_model_role_addresses`, `intervention_role_addresses` and `weight_edit_role_addresses` give the address form beside the name maps. venngram is pinned at `d7201de4`, its main with the role addresses. ([#875](https://github.com/speediedan/interpretune/issues/875))

- `Capability` holds the core surfaces only (`INTERVENTION`, `CAPTURE`, `GRADIENTS`, `LATENT_MODELS`). Techniques are bound to the component implementing them: an op names them in `required_techniques`, a component declares a typed `TechniqueSupport` record per technique in `technique_support` (`AttributionGraphSupport`, the new `HeadAttributionSupport`), and the gate resolves each to exactly one provider before anything runs, refusing a missing, ambiguous or mistyped implementation by name. A third party's technique is a record subclass and its ops, with no enum edit. `Capability.ATTRIBUTION_GRAPH`, `Capability.HEAD_ATTRIBUTION`, `ModuleCapabilities.attribution_graph` and the `attribution_graph_support` property are removed, and their spellings are no longer capabilities ([#984](https://github.com/speediedan/interpretune/issues/984))

- The `instrument` role kind is `artifact`, following venngram (speediedan/venngram#77): a tensor applied in every forward pass but never thawed, optimized or checkpointed, because it is reloaded from its published or saved source, and the only kind a schedule may promote to `latent:<name>`. Every role interpretune declares uses the new name: a circuit-tracer composition's transcoders, a frozen latent model or spliced SAE, and a weight edit's operand (`role="artifact"`, the default). A schedule writes `role:artifact` and `promote: {"role:artifact": "latent:<name>"}`. venngram still reads `role:instrument` as `artifact`, with a deprecation warning, until its 0.2 release. finetuning-scheduler is pinned at `edad6359`, its main with the same rename (speediedan/finetuning-scheduler#218). ([#962](https://github.com/speediedan/interpretune/issues/962))

- `attach_intervention(..., frozen=)` says which frozen role the intervention takes: `frozen="fitted"` for a value computed in the run (checkpointed, never optimized, so a resumed run keeps it) or `frozen="artifact"` for one loaded from a published or saved source (reloaded, never checkpointed). `frozen=True` is refused: it declared `instrument`, so an intervention computed in the run and attached frozen was left out of every checkpoint and lost on resume. ([#962](https://github.com/speediedan/interpretune/issues/962))

- One capability namespace: `ModelBackendCapability` and `AnalysisBackendCapability` are replaced by `Capability` (`INTERVENTION`, `LATENT_MODELS`, `GRADIENTS`, `CAPTURE`, `ATTRIBUTION_GRAPH`, `HEAD_ATTRIBUTION`), and `ACTIVATION_INTERVENTION` and `FEATURE_INTERVENTION` merge into `INTERVENTION`, whose `InterventionSupport` record mirrors venngram's `Support` (`ops`, `targets` of `activation`, `units` and `features`, `position_scopes`, `values`, `bases`, `of`). circuit-tracer's `FeatureInterventionSupport` becomes `FeatureTargetSupport`, the detail of its `features` target, and its `feature_intervention_support` property is its `intervention_support`. Components keep existing (a model backend, an analysis backend) and each declares `capabilities`, a record per capability and `requires`: circuit-tracer's analysis backend requires `GRADIENTS` and `LATENT_MODELS`, and `get_module_capabilities` refuses a requirement no other component provides. `ModuleCapabilities` lists each capability's providers (`providers`) and keeps one intervention record per provider, so a target two components reach is kept and `intervention_for(target)` refuses an unqualified request for it (`intervention_for(target, provider=...)` names the path). `PositionScope.POSITIONS` names the explicit positions a feature tuple carries. The spellings `activation_intervention` and `feature_intervention` are refused with `intervention`, the module-level `analysis_capabilities` property is removed, and the conformance report format is `interpretune.conformance.report/2`, its declarations keyed by capability and provider ([#951](https://github.com/speediedan/interpretune/issues/951))

- Intervention ops: `InterventionMode` is removed and an op is a name validated against venngram's registry (`venngram.ops.OPS`). `InterventionSpec.mode` is `op`, the payload key `mode` is `op`, the shorthand field `intervention_mode` is `intervention_op`, and `required_intervention_modes` is folded into `required_ops`, which names composition ops and tensor ops alike (the loader partitions them; the tensor ops are an op's `required_tensor_ops`); the retired spellings are refused. An executor registry keyed by op name (`interpretune.analysis.backends.ops`: `register_executor`, `executor_for`, `registered_ops`) replaces the branch chain that applied the seven core ops, which it registers from the shared op math together with `replace_with_error`. A backend whose hook computes its edit during the pass declares every registered op (`InterventionSupport.every_registered_op`), including ops registered later, and `InterventionSupport.declared_ops` reads the current set. An op collection's definition may carry an `op_spec` block instead of schemas, making it a tensor op: loading it, under the hub trust opt-in, registers its `OpSpec` with venngram and its executor here with the collection, version and revision as provenance, after checking on a probe that the implementation is shape-preserving, out of place and differentiable in the activation and the operand. The op-definition cache format is 9 ([#952](https://github.com/speediedan/interpretune/issues/952))

### Added

- `export_graph_subset` (`interpretune.analysis.venngram`): a circuit-tracer attribution graph, pruned or whole, written as a venngram `graph_subset` document (#966, slice 2), the inverse of applying one. Each selected feature is a node at its source layer, position and feature index with its activation, anchored `from_end` by default (or `absolute`, `token_match` with the source tokenizer, or `all`); the attributions between exported features are its edges, and the source prompt, attribution targets and pruning settings its provenance. venngram checks the document as its reader would, and an exported graph applies again through `recipe_feature_interventions` ([#966](https://github.com/speediedan/interpretune/issues/966))

- PyTorch profiler summaries in the core loop: with `profiler_cfg.pytorch_profiler_cfg.filename` set, the train, test and analysis loops write a table of the last profiled window's operators to `<trace_dir>/<phase>-<filename>.txt`, shaped by `sort_by_key`, `row_limit` and `max_name_column_width` (the names Lightning's `PyTorchProfiler` and finetuning-scheduler's example `ExtendedPyTorchProfiler` use), from configuration or the core CLI. An unknown sort key, or a summary option without `filename`, is refused when the configuration is built. The configuration guide gains a PyTorch profiling section with a core loop and a Lightning (`--trainer.profiler`) example, and both examples run in the test suite as written ([#11](https://github.com/speediedan/interpretune/issues/11))

- Native latent frame and chart edits: `latent_edit_spec` compiles a frame or chart edit of one feature block into a spec that runs inside a forward pass at the latent sub-hook of the model the block belongs to, on both CPU backends, with its token scope independent of the block. The ops (`frame_replace`, `chart_set`, `chart_path`, `chart_rotate`, `chart_scale_norm`) are tensor ops in a bundled `latent` op collection; each edits the block's decoded contribution with the catalog's own function and writes back the minimum-norm change of the block's activations, scaled by the spec's operand (the dose). Both backends refuse, before any pass, an edit whose attached latent model is not the one its target resolved to or whose decoder rows have changed, and an edit on the gradient flow. `block_edit_spec` writes a whole block's `set`, `ablate` and `scale_norm` as core ops on its columns. `InterventionSpec` gains `params` (op parameters the scalar fields do not carry), and an op collection's tensor op may name a `probe` its contract is checked on, for an executor that reads its context from `params` ([#1091](https://github.com/speediedan/interpretune/issues/1091))

- The `prompt_analysis` example component (`speediedan/prompt-analysis`): a task-neutral component for analyses of free-form prompts, with no dataset, label or task head. Its prompt configuration (`PromptSetConfig`, or `ChatTemplatePromptSetConfig` for instruction-tuned models) carries the prompts, and `PromptDataModule` serves them, tokenized, as the test and predict splits; the train and validation splits are refused by name, and so is an empty prompt set at setup. The model-only configurations (`prompt_analysis.gemma2.circuit_tracer`, `...gemma2.circuit_tracer+nnsight`, `...gemma3.circuit_tracer+nnsight.neuronpedia`) set no prompts and no attribution targets; the `capital_states` variants carry the capital prompt the circuit-tracer notebooks analyze, with the intermediate city and the answer as targets ([#1013](https://github.com/speediedan/interpretune/issues/1013))

- Latent addresses, frames, charts and linear spaces (`interpretune.analysis.venngram`): a `LatentCatalog` resolves `features:` and `subspace:` addresses to whole blocks of loaded latent models (a declared block size, so an SAE feature and a block-sparse featurizer's block share one address form) and to named subspaces, with external ids resolved only through declared aliases. Coordinates inside a block are read and replaced only in a named, exactly versioned orthonormal `LatentFrame`, checked against the current decoder rows; a `LatentChart` (registered kinds, `affine` and `pca_plane` built in) edits them in chart coordinates (`set`, `path`, `rotate`, `scale_norm`), and charts travel in an address book's `charts` key; a `LinearSpace` reads features expressed in a mapped space, such as `space:jlens`, and writes edits back exactly through the map's declared inverse or pseudoinverse, refusing a map that cannot be written exactly ([#865](https://github.com/speediedan/interpretune/issues/865))

- Bounded remote-session tuning for nnsight compositions served remotely (NDIF), in `interpretune.tuning.remote`: a remote session trains only the adapter or intervention tensors it creates, with their optimizer and loop, against the frozen served base, and a run is a sequence of bounded chunks. `run_remote_chunk` runs one chunk inside `model.session(...)` and returns a `RemoteChunkState` (role tensors, optimizer state, step, data cursor and RNG state, as plain tensors), and `RemoteCheckpointLedger` commits a returned chunk only on top of the previous one, refusing another model revision, role layout or schedule, a gap, a conflicting duplicate or tensors on the meta device. Tested against a plain-torch oracle, for chunked resume against an uninterrupted run, through nnsight's local simulation, and in a separate process holding its own model copy; not yet run on NDIF. The remote tunable view's refusal now names this route ([#775](https://github.com/speediedan/interpretune/issues/775))

- Cross-backend address conformance: `assert_same_selection(views, addresses)` in `interpretune.testing.conformance.tuning` resolves each venngram address on every view it is given (compositions of one model, by backend) and checks that the selections are the same tensors of the wrapped model, compared by the wrapped model's own names (`wrapped_model_names`, `selection_by_wrapped_name`). It names the address and each backend whose selection differs, or on which the address does not resolve. Interpretune's tests run it on GPT-2's core/HF, nnsight and TransformerLens compositions, for addresses by layer, component, parity and fraction of the depth, and for latent models spliced by site address. The tuning pages show the address form beside the name form. ([#875](https://github.com/speediedan/interpretune/issues/875))

- Direct per-unit interventions: venngram addresses select model units for `add`, `scale`, `replace` and coordinate `clamp`, with token scope independent of unit selection. Unit recipes and export support selected `replace`; selected clamps remain direct payloads because venngram's recipe registry has no unit-clamp target. `UnitIntervention` and unit-addressed tuning configurations train only the selected values, and `normalized_unit_doses` converts doses using a measured residual norm and an explicit down-projection weight layout. ([#867](https://github.com/speediedan/interpretune/issues/867))

- The concept-direction latent-dynamics notebook in the examples gallery: the color-vs-fruit concept direction built from each state `gemma-3-1b-it` computes (token embeddings, answer-position states, context states) and compared stage by stage through their alignment, a readout after the final norm, causal steering at block 10, each stage's attribution-graph features, and UMAP projections of the states and directions. It fetches the analysis from the `speediedan/concept-direction` Hub component at a pinned revision and runs it only once the reader opts into that component's code ([#971](https://github.com/speediedan/interpretune/issues/971))

- Hook interventions support explicit position sets with one operand per selected padded-tensor position.

- Weight-space ops and unit addresses on TransformerLens compositions: a `TransformerBridge`'s view resolves the wrapped model's component map through the modules the bridge wraps, so each tensor takes the unit axis the map row's `layout` gives the wrapped model's own tensor (`unit_dim`), as it already took that tensor's layer and component. `weight_form`, `weight_form_site_widths` and the `weight_equivalence_check` op now run on the bridge (the four weight-form conformance cases pass on the `TransformerBridge` target instead of skipping), and a weight an applied edit parametrizes keeps its place under the name the model holds it by ([#1055](https://github.com/speediedan/interpretune/issues/1055))

- `AnalysisRunnerCfg.writer_batch_size`, forwarded to the analysis store's `Dataset.from_generator`: how many records the writer buffers before each flush to disk. Peak host memory during generation follows this times the record size, not the number of records (measured: 2,000 and 4,000 records of 1 MiB both peak at 779 MiB at a batch of 50, against 11.8 GiB at the default 1000), so analyses with large records can lower it. `None` keeps the `datasets` default, and a non-positive value is refused by name ([#203](https://github.com/speediedan/interpretune/issues/203))

- FSDP2 memory profiling in the core loop: with `track_fsdp_mem` and `training_step` under `collect_funcs.fsdp`, each rank of an `fsdp2` run writes an `FSDP2MemTracker` report for every profiled training iteration (the per-category peak and the module-wise forward and backward states, with its JSON form in `rank_<r>_fsdp_memory_report.json`). The tracker is built at the first profiled iteration over the sharded module and the loop's optimizer, and an empty `fsdp_mem_tracker_root_module` names the root `fully_shard` wrapped (the interpretune module). Under `FTSCoreCallback` each report records the schedule depth it ran at, and the tracker is rebuilt over the optimizer each phase transition installs ([#881](https://github.com/speediedan/interpretune/issues/881))

- The venngram integration applies attribution-graph subsets from one prompt in another (#966, slice 1). An op that targets a graph subset (`target: {graph: <name>}`, venngram's `graph_subset` documents) becomes circuit-tracer feature tuples through `recipe_feature_interventions(..., token_ids=, tokenizer=)`: each transcoder or CLT node at the stage's site is placed by its anchor in the destination prompt (absolute, from the end, token-matched, or every position), the whole plan refused if any node does not resolve or two land on one coordinate. `replace` sets the node's column, or its delta from a baseline column, and `add` sets the feature's clean activation plus it, through `scale` and `abs`. A restriction (`outside`) is refused by name; block-sparse nodes and the model-backend surface are not yet supported and are refused by name too. `venngram_feature_subsets` derives the path's `circuits.subsets` declaration from the feature record, and `check_recipe(..., analysis_backend=True)` checks graph ops against it. It needs speediedan/venngram#105, which venngram's pin (`d7201de4`) includes ([#966](https://github.com/speediedan/interpretune/issues/966))

- The `knowing_using` example component (`speediedan/knowing-using`): the Knowing-Using Gap's layer-wise representation self-distillation (LRSD) recipe from Dai et al. ([arXiv 2607.08393](https://www.alphaxiv.org/abs/2607.08393)) on Qwen2.5-1.5B-Instruct, as one LoRA phase driven by `FTSCoreCallback` on the core loop. The loss is the completion cross-entropy plus $\lambda$ times the relative squared error between block 14's and the stop-gradient block 21's states over the fact's head-entity span (`lrsd_lambda: 0.0` is the plain arm), and `ExactMatchReport` scores the unique two-hop and single-hop questions by greedy exact match before training and after every epoch. The datamodule draws the paper's 1,000-fact sample (fact seed 848) from the paper's chaining tasks, downloaded from the Hub dataset `speediedan/knowing-using-gap-chaining` at a pinned revision unless `data_path` names a local copy. A tuning page (`docs/tuning_knowing_using.md`) describes the recipe, the data, how to run both arms and their cost on one GPU ([#931](https://github.com/speediedan/interpretune/issues/931))

- Per-build telemetry for the GPU pipeline (`tests/gpu_ci/build_telemetry.py`), published beside the phase evidence as `it-phases/telemetry/build_telemetry.json`. It joins the planner's record (`plan_gpu_run.py --record`: the build's identity, the mode and why, the selected areas and the change set) with each phase's selected count, outcomes and full-phase denominator (a selected run collects the phase again without its selection file, at the same revision), each phase class's interval, and each lease stage's waits, acquisition with the device UUIDs it covers, and release (`.azure-pipelines/scripts/telemetry.sh` events from `gpu_phase.sh` and `gpu_stage_lease.sh`). A report is joined only to the manifest whose digest it records, at the plan's revision, and evidence that does not bind is refused by name; anything missing is listed in `unknowns` rather than counted as zero. The whole-server lease is released in its own step before the evidence is published, so its release is recorded ([#741](https://github.com/speediedan/interpretune/issues/741))

- An on-demand GPU CI report (`python -m tests.gpu_ci.ci_report`) over a window of builds: per week, builds by reason, GPU-agent, test-task and device-held minutes and selected against full counts on gated builds; for each full run of main, every failure classed against the gates of the pull requests merged since the preceding green full run (`selected`, `miss`, or `undetermined` where a merge has no readable gate evidence); and the time from each merge to the first full run containing it. Unknown quantities stay unknown rather than zero ([#741](https://github.com/speediedan/interpretune/issues/741))

- `interpretune.harness.sessions.resolve_model_spec` and `experiment_session` take `model_specs=`: a mapping in the spec file's schema, a local path, or a `hub://<org>/<repo>@<revision>/<path>` reference into a cached component. A published experiment can then name the models it supports in its own repository instead of in interpretune's bundled `model_specs.yaml`, which stays the default. A refusal names the source it searched ([#1025](https://github.com/speediedan/interpretune/issues/1025))

- The tuning seam takes venngram site addresses: `attach_intervention`, a configured intervention's `site` and a `LatentSite`'s `read` and `write` accept an address selecting one site, such as `point:hook_resid_post & layers:13`, beside a module path. `interpretune.tuning.sites.resolve_site` resolves it on the composition: on TransformerLens through the hook points it exposes, in any spelling the activation-point vocabulary knows, and on core/HF and nnsight through the architecture's component map, under the HF model's path. An address that resolves to a module's input is rewritten before the module runs. An address selecting several sites or a gradient, or naming a point the composition cannot place, is refused, naming it. ([#864](https://github.com/speediedan/interpretune/issues/864))

- The notebook helpers several example tutorials share are supported API in `interpretune.harness`: `notebook_ui` renders target gaps, top-feature comparisons, steering results, concept-token positions, the feature decoupling table, the decoder projection map and the J-space readout comparison, and `notebook_inputs` provides `required_os_env`, `concept_token_positions` and `feature_io_profiles`. `it_examples.utils.nb_ui_utils` and `example_helpers` keep only the helpers a single tutorial uses and re-export the promoted names until the notebooks move; helpers no tutorial called are removed ([#1016](https://github.com/speediedan/interpretune/issues/1016))

- Gradient interventions: `model_bwd_intervention` applies the payload `model_fwd_intervention` takes to the gradient at each hook point during a backward pass, through the same op executors, and stores the gradients at its `grad_capture` sites from a baseline and an intervened pass. Both model backends implement `bwd_w_intervention` (`SupportsGradientIntervention`: hooks on the activations' tensors under TransformerLens, NNsight's `.grad`) and declare `of: [value, grad]` in their `InterventionSupport` (`InterventionSupport.every(of=...)`), and `require_intervention_support(..., flow="grad")` refuses a backend that declares values only. `recipe_interventions(..., flow="grad")` translates a recipe's ops on `of: grad` targets for it, and `check_recipe` takes the same `flow`. `interpretune.analysis.venngram.resolve_sites` resolves a venngram site address (`point`, `layers` and `of`, with set algebra and `@<set>` references) to the hook names it selects and the flow it acts on, and `grad_capture` accepts one. A model whose parameters are frozen, as a circuit-tracer composition leaves it, works too: the backward pass makes the sites it reads carry gradients (`track_gradient`) rather than finding nothing to differentiate ([#938](https://github.com/speediedan/interpretune/issues/938), [#970](https://github.com/speediedan/interpretune/issues/970))

- Readouts: the scalar a gradient intervention differentiates is a `Readout` (`interpretune.analysis.backends`), `fn(logits, activations)` over the activations at the sites it names, from the forward pass the backward runs from, so it can be a logit difference, an intermediate activation's projection onto a direction, or a latent model's feature activation rather than only last-token logits. `bwd_w_intervention` takes it as `readout` (a callable of the logits is a readout reading no sites), both model backends keep the activations it reads, and a gradient captured or edited at a site it reads includes its contribution there. Both backends now edit a copy of the gradient: at a residual add autograd hands one gradient tensor to both branches, so an edit at an attention output, written in place, also edited the residual stream's gradient. `model_bwd_intervention` takes one as its `readout` input, defaults to `last_token_logit_readout` over `logit_target_ids` (the metric it used before), and refuses a readout beside `logit_target_ids`. A treatment's declared readout (venngram's `readout`: a weighted sum of `sum`, `project` and `norm` terms over book sets at a token scope, the logits included as `unembed.hook_out`) executes as a `Readout` through `recipe_readout`, beside the payload `recipe_interventions(..., flow="grad")` translates; the executors are checked against venngram's conformance vectors, `register_readout_executor` adds one for a reduction registered in venngram, the support record declares the reductions executed (`readouts`), and gradient stages declaring different readouts are refused, since one backward pass differentiates one scalar ([#1024](https://github.com/speediedan/interpretune/issues/1024))

- Tensor parallelism in the core loop: `SessionRunnerCfg.placement='tp'` splits the layers `tp_plan` selects across a one-dimensional mesh of every rank, with finetuning-scheduler's tensor-parallel plan grammar (the keys of `fsdp_plan`, each mapped to a parallel style such as `colwise` or `rowwise`). Rank 0's weights are broadcast before the split, and every rank takes the whole dataset in one shared order. A plan that splits the views of a packed weight (a TransformerLens bridge's q, k and v, views of its joint `qkv`) splits the packed weight with them, so views and packed weight keep sharing storage through training; a split that would cut a parameter from storage it shares any other way is refused by name, as are a plan for the other kind of placement and a model built on the meta device. A latent model spliced inside a split layer (`tuning.latents`) reads the whole activation and rewrites each rank's shard: the splice gathers an activation that arrives as a `DTensor` (a `tp_plan` entry with `use_local_output: false`) and lays its reconstruction out as the output it replaces, and a splice at a split layer that hands on its local shard as a plain tensor is refused at placement, naming the site. Phased tuning through `FTSCoreCallback` and resuming from a distributed checkpoint work under `tp` as under `fsdp2`: split weights and their optimizer state load back into the split layout. Under `tp` every optimizer steps one tensor at a time (`foreach=False`, including on the groups a tuning scheduler adds), since a parameter group can hold split and whole parameters, which torch's multi-tensor and fused kernels (the CUDA default) cannot take together; an optimizer asking for `foreach` or `fused` is refused by name. Without a `tp_plan`, the core and nnsight compositions use the plan transformers declares for their Hugging Face model (`hf_tp_plan`): attention and MLP projections split the Megatron way, the embedding and LM head left whole; a declared style it does not translate, or head counts the world size does not divide, are refused by name, and a model declaring no plan (or a TransformerLens bridge) needs an explicit one.

- Published dashboard corpora are discovered through Hub collections whose items are buckets: `find_dashboard_corpora(model_id, source_set_id)` lists them with what each corpus's own `dashboards.json` says (prompt corpus, layers, prompt and token counts, page index), reading collections anonymously unless `collection_token=` is given. `publish_dashboard_run(..., collection=)` and `scripts/publish_dashboards_to_hub.py --collection` register a published bucket once every check has passed, with a separate `collection_token` for `collection.write`; a dataset-store publish naming a collection is refused before the upload. The project's collection, `speediedan/neuronpedia-dashboard-corpora`, is the default trust list (`DEFAULT_CORPUS_COLLECTIONS`) ([#262](https://github.com/speediedan/interpretune/issues/262))

- Pre-publish checks as one interface (`interpretune.utils.publish_checks`): each check is named, an unknown name in `skip_checks` or `add_checks` is refused, and a check that cannot tell does not pass. Dashboard publishing runs `page-index`, `manifest-consistency`, `bucket-prefix` and an advisory `row-group-size` report before any network call. A post-upload `range-read` check reads one published Parquet file back through `HfFileSystem` and checks that it decodes; it is on by default for the bucket store and for `push_analysis_store`, and its failure (`PublishedArtifactCheckError`) says the artifact is already live. `push_analysis_store` takes `skip_checks` and `add_checks` and records skips in the envelope's `provenance`. The `datasets` floor rises to 4.1.0, the first release that page-indexes every Parquet file `push_to_hub` writes ([#262](https://github.com/speediedan/interpretune/issues/262))

- A TransformerLens composition applies `hf_from_pretrained_cfg.lora_cfg`. The adapters are added to the HF model in place before the `TransformerBridge` wraps it, so the bridge runs them, and after bridging only the LoRA tensors train (the bridge's own split q, k and v included in the freeze). They take the `adapter:<name>` role, so a schedule thaws them with `role:adapter`. A target the bridge never calls (GPT-2's fused `c_attn`, which the bridge splits into its own q, k and v) is refused after a one-token forward finds it, naming the module, and a `lora_cfg` with a `bitsandbytesconfig` is refused at configuration, since `TransformerBridgeView` refuses quantized parameters. The setting was accepted before and silently dropped, so the run tuned the base model. - The default optimizer (`optimizer_parameters()`) covers an attached, trainable view's root parameters, less `fitted` and `instrument` tensors: every view is rooted at the interpretune module, so trainable modules registered beside `module.model` (interventions, spliced SAEs) are optimized with no adapter extending the hook. Compositions without a view, or with a refusing one, keep the model's own parameters (#761)
- `interpretune.tuning.core_loop.FTSCoreCallback` drives finetuning-scheduler's `TuningScheduler` from the core training loop (`SessionRunnerCfg.callbacks`): the tuning scheduler is built over the session's module and its view, its optimizer and lr schedulers are installed as the module's, and its epoch, step and end boundaries, transitions and stops follow the loop's. - `FTSCoreCallback` builds `tuning_scheduler_kwargs` values given as `class_path` mappings (a transition policy, a checkpoint policy, a list of gates) when it builds the tuning scheduler, so a core-loop fine-tuning run's policies come from its configuration while the callback's arguments stay plain configuration ([#847](https://github.com/speediedan/interpretune/issues/847))

- A run chooses its finetuning-scheduler view in configuration: `it_cfg.tunable_view` (a `class_path` and `init_args`) is instantiated with the module as the view's root, ahead of the composition's `build_tunable_view()`, and a view class taking `roles` receives the composition's roles. A TransformerLens composition can then schedule its own (physical) parameter names (finetuning-scheduler's `CanonicalView`) or turn the implicit norm thaw off (`TransformerBridgeView` with `implicit_norm_thaw: false`) with no subclass, as the retired strategy adapter's `model_view_cfg` allowed. `TransformerBridgeView.to_physical` resolves the physical name of a parameter no TransformerLens name reaches (a norm TransformerLens does not name, a fused projection) to itself, so a schedule can name it exactly. A phased parity run covers each mode, and the committed phase collection manifest is re-measured ([#841](https://github.com/speediedan/interpretune/issues/841))

- Unit adapters (`interpretune.tuning.weights.attach_unit_adapter`): tune only the selected units of the tensors an address selects, through a trainable delta over those units' slices along each tensor's unit axis ($W = W_0 + \Delta$, zero at first, applied by parametrization). Its tensors take the role `adapter:<name>`, so a schedule thaws them by role, and `remove()` restores each tensor exactly. A site target (`point:mlp.out.hook_in & layers:12`) projects its units onto the parameter slices they are: neuron $n$ of the MLP's hidden layer is column $n$ of the down projection and row $n$ of the up and gate projections. A tensor whose unit axis the view's component map does not record, or a unit outside it, is refused ([#868](https://github.com/speediedan/interpretune/issues/868))

- A TransformerLens composition's tunable view supplies structure (`TransformerBridgeView.structure()`), so a schedule's venngram addresses (`layers:9 & component:attn.*`) select the same tensors on it as on the core/HF and nnsight compositions of the same model. Each tensor is placed through the component map of the model the bridge wraps: the bridge rewires that model in place, so the view recovers each tensor's original name from the names its components record and locates it with the map of a skeleton built on the meta device. Without a published map, the view keeps venngram's physical structure, which places no components ([#1045](https://github.com/speediedan/interpretune/issues/1045))

- An intervention payload key, or `intervention_hook_pattern`, may be a venngram site address (`point:hook_resid_post & layers:13`), which names one activation the same way on every model backend. It expands like a layer wildcard to the sites it selects, in layer order, on both the forward (`model_fwd_intervention`) and backward (`model_bwd_intervention`) surfaces, and a backward capture may name one too. A site the model does not expose is refused rather than mapped onto a nearby hook, and an address on the other flow (`of: grad` on the forward surface, or its absence on the backward one) is refused ([#876](https://github.com/speediedan/interpretune/issues/876))

- Latent models and interventions take the layer and component of their site in the module's tunable view, although they are registered beside the model (`latent_models.<name>`, `interventions.<name>`). A schedule then selects them by depth: `role:latent & layers:12:` thaws the latent models spliced at layers 12 and above. Each module declares the placements in its cooperative `tunable_placements()` (`latent_model_placements`, `intervention_placements`), which `default_view(attached=)` passes to venngram's view and `TransformerBridgeView(attached=)` resolves through the bridge component holding each site; a site no map row places is left unplaced, with a warning ([#875](https://github.com/speediedan/interpretune/issues/875))

- A splice site may reference an address book's named set (`@resid13`), so one shared book names it on every backend: `attach_intervention(..., sets=)`, `attach_latent_model(..., sets=)` and `resolve_site(..., sets=)` take the book's sets (`interpretune.tuning.sites.book_sets`, from an `AddressBook`, a book document, a local path or a venngram store reference), and `InterventionCfg.book` names the book a configured intervention's site reads ([#876](https://github.com/speediedan/interpretune/issues/876))

- A circuit-tracer composition's tunable view places each per-layer transcoder's tensors at the layer whose MLP it replaces (`CircuitTracerView.structure()`), so a promotion names a layer range by address: `promote: {"role:artifact & layers:-4:": "latent:transcoder"}`. A cross-layer transcoder's tensors locate at no layer ([#875](https://github.com/speediedan/interpretune/issues/875))

- A unit splice takes its units from an address book entry: a site that references a named set (`@steer`) whose address names units configures the same `UnitIntervention` as the literal address, rather than a full-width operand ([#876](https://github.com/speediedan/interpretune/issues/876))

- The attention-attribution notebook's intervention arms are venngram site addresses over a small address book (`@attn`, `@mlp`, and the stack's halves `@early` and `@late`), resolved per model by `resolve_intervention_arms` in the notebook helpers, and the notebook runs the same arms on a second model family (Llama 3.2 1B by default, the `second_model` parameter) as a plain `(core, nnsight)` composition, with the same positive control ([#1016](https://github.com/speediedan/interpretune/issues/1016), [#876](https://github.com/speediedan/interpretune/issues/876))

- A plain `(core, nnsight)` composition is its own model backend: the ops that run the model (`model_fwd_intervention`, `fwd_w_cache` and the rest of the model-backend surface) no longer need a latent adapter composed to reach the NNsight backend. An architecture the hook mapping does not cover still loads, without a backend. `NNsightModelBackend.for_model` builds the backend for a model's architecture, which the sae_lens and circuit-tracer compositions now use too ([#1103](https://github.com/speediedan/interpretune/issues/1103))

### Changed

- `ITLensSharedConfig.default_padding_side` is retired: passing it to any TransformerLens configuration (`ITLensBridgeConfig`, `ITLensFromPretrainedConfig`, `ITLensCustomConfig`) raises a `TypeError` naming it. The adapter never applied it, since the bridge wraps the datamodule's tokenizer, which is built from `tokenizer_kwargs` before the bridge exists, so a configuration that relied on it alone silently got the tokenizer's own padding side. Set `tokenizer_kwargs.padding_side` instead, as every shipped configuration already did. `NNsightConfig.default_padding_side` is unchanged. With it gone, `tokenizer_kwargs.padding_side` is the one place a TransformerLens or SAELens composition's padding side is set: `TLensGenerationConfig.padding_side` stays an optional per-generation override that follows the tokenizer when unset, and the gemma2 benchmark configurations no longer repeat it ([#1081](https://github.com/speediedan/interpretune/issues/1081), [#126](https://github.com/speediedan/interpretune/issues/126))

A GPU device that torch cannot provide raises, where a model is placed on it rather than when its config is built (the TransformerLens `device`, an nnsight `device_map`, an HF `pretrained_kwargs.device_map`), so a configuration written for a GPU and placed elsewhere before loading is unaffected.
